## 1. 배경 및 목표

### 1.1 현재 구조

수집은 **push 기반 단방향**이다. Rust agent(`agent/src/`)가 CPU·메모리·디스크·네트워크·로그·웹 로그를 수집해 Prometheus로 보내고, log-analyzer가 `log_error_total` 을 조회해 LLM으로 분석한 뒤 admin-api를 거쳐 Teams·인시던트로 흘린다.

이 구조의 한계는 **LLM이 "이미 수집된 것"만 볼 수 있다**는 점이다. 분석 도중 "이 시점에 디스크가 찼나?", "해당 JEUS 프로세스가 살아 있나?", "커넥션이 몇 개나 물려 있나?" 같은 추가 확인이 필요해도 확인할 방법이 없어, LLM은 추측하거나 "확인이 필요합니다"라는 결론으로 끝난다.

### 1.2 목표

1. LLM이 분석 중 **추가 근거가 필요하면 대상 서버에서 진단 명령을 실행**하고, 그 결과를 다시 분석에 투입한다.
2. 원인이 확정되면 **예방 조치 명령을 실행**해 장애로 번지기 전에 끊는다.

**목표는 자율 예방이다.** 사람이 먼저 물어봐야 동작하는 구조가 아니라, 스케줄러가 이상 징후를 잡은 시점에 LLM이 스스로 근거를 보강해야 한다. 이 구분이 중요한 이유는 §3.1에 있다 — 현재 명령을 실행할 수 있는 표면이 전부 사람이 시작하는 경로이기 때문이다.

### 1.3 전제

각 대상 서버에 SSH 접근이 가능하다. 폐쇄망 RedHat 8.9 + Docker Compose 환경이며, 대상 서버는 백화점 운영계다.

## 2. 핵심 발견 — 이미 확보된 자산

이 기능은 **새 신뢰 경계를 만드는 것이 아니라 이미 운영 중인 패턴의 확장**이다. 코드베이스 확인 결과:

| 자산 | 위치 | 이 기능에 대한 의미 |
|---|---|---|
| **키 기반 무인 SSH** | `services/ssl_deployer.py` | `SSL_DEPLOY_KEY_PATH` RSA 키로 사람 개입 없이 원격 명령 실행 + 파일 배포 중. 서버 등록 시 `authorized_keys` 자동 등록. **무인 원격 실행은 이미 이 코드베이스의 위협 모델에서 수용된 패턴** — Phase 1의 존재 증명 |
| 대화형 SSH 실행 | `services/ssh_session.py` | `ssh_exec(host, port, user, password, command)` 존재. 단 **사람이 입력한 비밀번호를 인메모리 5분 슬라이딩 TTL로만 보관**(DB 저장 금지). 무인 실행 경로로는 사용 불가 |
| SSH 원격 제어 실적 | `routes/agents_control.py` | start/stop/restart/status/install/config를 이미 SSH로 실행 중. 세션 계정과 `agent_instances.ssh_username` 일치 검증(`_assert_session_account`) 보유 |
| 도구 레지스트리 | `chat_tools` 테이블 + `services/chat_tools/executors/` | executor 5종(ems/admin/log_analyzer/qdrant/prometheus). DB 기반 등록 + `is_enabled` 토글 + `input_schema` JSON Schema. **신규 executor 추가는 확립된 패턴** |
| 인젝션 하드닝 선례 | `services/agent_utils.py` `sanitize_promql_label` | 외부 입력이 쿼리 문자열에 섞이는 지점을 화이트리스트로 막는 기존 관행 |
| 승인 워크플로우 선례 | `alert_feedback` pending→approved/rejected + `routes/incidents.py` | Phase 2 승인 게이트가 참고할 기존 UI·권한 모델(admin 또는 지정 승인자) |
| Rust agent | `agent/src/` | **수집 전용 — 명령 실행 기능 없음**. 실행 지점으로 삼지 않는다 (수집기에 exec를 넣으면 전 서버에 원격 실행 표면이 상시 열린다) |
| **SSH 의존성 소재** | `admin-api/requirements/base.txt:13` `paramiko>=4.0.0` | **log-analyzer requirements에는 paramiko가 없다.** SSH 실행 능력은 admin-api에만 존재하며, 이 사실이 진단 루프의 위치를 결정한다(§4.1) |
| **진단 루프 삽입 지점** | `services/prometheus_analyzer.py:738-764` | 이상 감지 후 이미 Qdrant에서 과거 해결책을 조회해 `solution_ctx` 로 프롬프트에 붙이고 있다. 진단 결과도 **동일한 컨텍스트 보강 슬롯**으로 들어간다 — 새 구조가 아니라 슬롯 추가 |
| **호스트별 쿨다운** | `prometheus_analyzer` `_record_sent(host)` + `PROM_ALERT_COOLDOWN_SECONDS`(기본 1800) | 스케줄러가 5분마다 돌아도 같은 호스트 실행은 30분에 1회로 이미 제한된다. **명령 폭주 방지 장치가 기존에 존재** |
| 자동 분석 경로의 한계 | `prometheus_analyzer.py:764` `call_llm_text()` / `analyzer.py:408` `call_llm_structured()` | 둘 다 **단발성 호출** — 루프도 도구 디스패처도 없다. 도구 호출 루프(`run_tool()`)는 `chat_agent.py` 에만 존재. **자율 경로에 루프를 새로 만들어야 한다** |

## 3. 범위 분리 — 두 개의 독립 기능

이 요청은 하나의 루프처럼 보이지만 **위험 프로파일이 정반대인 두 기능**이다. 묶어서 설계하면 가치의 대부분을 차지하는 진단 기능이 조치 승인 설계에 발목을 잡힌다.

| | **Phase 1 — 읽기 전용 진단** | **Phase 2 — 변경 조치** |
|---|---|---|
| 예시 | `df -h`, `free -m`, `ps -ef`, `ss -s`, `tail`, `systemctl status` | 프로세스 재기동, 캐시 정리, 로그 로테이션, 임시파일 삭제 |
| 멱등성 | 있음 (반복 실행 무해) | 없음 |
| 상태 변경 | 없음 | 있음 |
| 사람 승인 | 불필요 (자율 실행) | **기본 필수.** 단 "이미 서비스 불능"이 메트릭으로 입증되는 항목만 예외적으로 자동 실행 허용 (§7.3, 현재 §5.3 1건) |
| 롤백 | 불필요 | 필요 (또는 검증 후 확정) |
| 출시 | **단독 출시 가능** | Phase 1 안정화 이후 |

**원칙: Phase 1을 먼저 단독으로 출시한다.** 근거 보강만으로도 LLM 분석 품질이 크게 오르고, Phase 2 없이도 운영자가 "무엇이 문제인지"를 훨씬 빨리 안다.

### 3.1 현재 트리거 표면 — 전부 사람이 시작한다

명령 실행을 붙일 수 있는 표면은 넷인데, **도구를 쓸 수 있으면서 동시에 자율적인 것은 하나도 없다.**

| 표면 | 위치 | 도구 호출 | 시작 주체 |
|---|---|---|---|
| 챗봇 대화 | `chat_agent.py` `run_react_stream` | **가능** (ReAct + `run_tool()`) | 사람 (질문) |
| 인시던트 자동 통찰 | `POST /chat/sessions/{id}/auto-insight` | 가능 (ReAct 엔진 재사용) | **사람 (✨ 버튼)** |
| 5분 주기 메트릭 분석 | `prometheus_analyzer.py` | **불가** (단발 `call_llm_text`) | 스케줄러 |
| 5분 주기 로그 분석 | log-analyzer `_scheduler` → `analyzer.py` | **불가** (단발 `call_llm_structured`) | 스케줄러 |

즉 **도구를 쓸 수 있는 곳은 자율이 아니고, 자율인 곳은 도구를 쓸 수 없다.** §1.2의 "자율 예방"을 달성하려면 스케줄러 경로에 도구 호출 루프를 새로 만들어야 하며, 이것이 rev.2에서 추가된 범위다. 챗봇 표면(US-1.1)은 부수적으로 함께 얻어진다.

## 4. Phase 1 요구사항 — 읽기 전용 진단

### 4.1 실행 주체 — 진단 루프가 도는 위치 (결정됨)

**결정: admin-api `services/prometheus_analyzer.py` 의 5분 주기 메트릭 이상 분석 경로.** 로그 분석 경로(log-analyzer)는 Phase 1 범위 밖.

| 근거 | 내용 |
|---|---|
| **① SSH 능력이 admin-api에만 있다** | `paramiko>=4.0.0` 은 admin-api requirements에만 존재. log-analyzer에 넣으려면 **개인키를 두 번째 컨테이너에 마운트**해야 하고, 그러면 "키를 나눠 영향 범위를 좁힌다"는 §7.1의 전제가 무너진다 |
| ② 호스트가 이미 해석되어 있다 | `prometheus_analyzer` 는 `HostContext(hc)` 를 **host 단위**로 순회한다. SSH에 필요한 호스트가 손에 있다. 로그 분석은 `system_name` 단위라 인스턴스 해석을 새로 해야 한다 |
| ③ 확인할 항목이 특정되어 있다 | `sm.anomalies` 가 "CPU 92%" 같은 구체적 이상을 담고 있어, 어떤 진단 명령을 고를지에 대한 입력이 LLM에게 명확하다 |
| ④ 삽입 지점이 이미 있다 | `call_llm_text()`(764행) 직전. 그 위에서 이미 과거 해결책을 `solution_ctx` 로 붙이고 있으므로 동일한 자리에 동일한 방식으로 들어간다 |
| ⑤ 폭주 방지가 이미 있다 | `_record_sent(host)` + 호스트별 30분 쿨다운. 5분 스케줄러여도 호스트당 30분에 1회 |
| ⑥ 목적에 맞다 | 메트릭은 **임계치에 접근 중인** 상태를 잡으므로 예방이 가능하다. 로그 분석은 이미 발생한 에러를 다루므로 본질적으로 사후 대응이다 |

| ID | 요구사항 |
|---|---|
| **FR-1.0** | 자율 진단 루프는 `prometheus_analyzer` 사이클 내부, **이상 감지 이후 LLM 호출 이전** 지점에 위치한다 |
| **FR-1.0-a** | 실행 빈도는 **기존 호스트별 쿨다운(`PROM_ALERT_COOLDOWN_SECONDS`)을 그대로 따른다.** 별도 예산 체계를 새로 만들지 않는다 |
| **FR-1.0-a2** | 다만 호스트별 쿨다운은 **사이클당 호스트 수를 제한하지 않는다.** 공유 스토리지 포화·네트워크 이벤트·불량 배포 시 수십 개 호스트가 동시에 임계치를 넘으면 그만큼의 동기 SSH 세션이 한 사이클에 몰린다(NFR-4의 스레드 점유 문제). 따라서 **① 동시 진단 SSH 세션 수 상한** 과 **② 사이클당 진단 대상 호스트 수 상한** 두 개의 정수를 둔다. 초과분은 다음 사이클로 미루며, 미룬 사실을 로그에 남긴다 |
| **FR-1.0-b** | 동일한 진단 카탈로그를 **챗봇 표면에도 도구로 노출**한다 (US-1.1). 카탈로그·검증·감사 로직은 두 표면이 공유한다 |
| **FR-1.0-c** | **log-analyzer는 SSH 개인키를 보유하지 않는다.** 향후 로그 분석·시간별 예측 경로에 진단이 필요해지면, admin-api가 내부 엔드포인트로 노출하고 log-analyzer가 호출하는 방식을 쓴다 |

### 4.2 자격증명 및 키 등록 (결정됨)

**결정: 진단 전용 키쌍 + 전용 OS 계정** (근거는 §7.1).

| ID | 요구사항 |
|---|---|
| **FR-1.10** | 진단용 SSH 키쌍은 **SSL 배포키(`SSL_DEPLOY_KEY_PATH`)와 분리된 별도 키쌍**이며, 대상 서버에서도 **전용 계정**을 사용한다 |
| **FR-1.11** | 공개키 등록은 **agent-v 설치 Job에 통합**한다. `POST /api/v1/agents/install` 은 이미 `X-SSH-Session` 비밀번호 세션으로 바이너리를 SFTP 업로드하므로, 같은 세션에서 `authorized_keys` 등록 단계를 수행한다. **운영자 절차는 늘어나지 않는다** (`ssl_servers.py:112-142` 와 동일한 의식) |
| **FR-1.12** | 등록 직후 **키 인증이 실제로 동작하는지 검증**하고(`verify_key_auth` 와 동등), 비밀번호는 DB에 저장하지 않는다 |
| **FR-1.13** | **이미 설치된 에이전트를 위한 소급 등록 경로**를 제공한다 (재등록 액션 또는 1회 마이그레이션). 설치 Job은 다시 돌지 않으므로 이것이 없으면 기존 서버 전체가 진단 불가 상태로 남는다 |
| **FR-1.14** | `authorized_keys` 등록 시 **`restrict` 옵션을 함께 기록**한다 (포트 포워딩·에이전트 포워딩·PTY·X11 차단). **`command=` 강제 명령은 v1에서 사용하지 않는다** — 근거는 아래 FR-1.14-a |
| **FR-1.14-a** | (FR-1.14 근거) `command=` 는 허용 명령 **집합**을 지정하는 옵션이 아니라 **단일 명령을 강제**하고 클라이언트 요청을 버린다. 따라서 카탈로그 8~12개(FR-1.1)와 양립하지 않는다. 2중 화이트리스트를 원한다면 `command=` 로 **강제 명령 디스패처 스크립트**를 지정하고 그 스크립트가 `SSH_ORIGINAL_COMMAND` 의 템플릿 ID를 자체 allowlist로 검증하는 방식이어야 하는데, 이는 **① 스크립트를 전 대상 호스트에 배포**해야 하고 **② 카탈로그가 admin-api와 온-호스트 스크립트 두 곳에 존재해 동기화 대상이 되며** **③ 카탈로그 항목 추가 시마다 전 호스트 재배포**가 필요하다. v1이 감당할 운영 비용이 아니다 |
| **FR-1.14-b** | 강제 명령 디스패처는 **Phase 2(변경 조치) 착수 시 재검토**한다. 상태를 바꾸는 명령에는 2중 강제가 비용을 정당화한다. 이때 FR-1.13의 소급 등록 경로를 재사용하므로 **"나중에는 못 들어간다"는 제약은 실재하지 않는다** — 재등록은 운영자가 비밀번호를 다시 입력하면 가능하다 |
| **FR-1.15** | `agent_instances.ssh_username` 이 변경되면 `authorized_keys` 는 해당 계정 홈에 종속되므로 **키 재등록이 필요**하다. 계정 변경 시 진단 가능 여부를 재검증한다 |

### 5.3 조치 카탈로그 항목 #1 — JEUS 행(hang) 복구

Phase 2의 **첫 번째 항목이자 자동 실행 부여가 검토되는 유일한 초기 항목**이다.

> **자동 실행 부여는 아직 확정이 아니다.** §9 Step 2가 자동 실행 판정 규칙을 산출하고 그 규칙이 검증된 뒤에 부여된다(FR-2.18의 "명시적 부여"에 해당). **그 전까지 이 항목도 다른 조치와 동일하게 승인 게이트를 거친다.**

**대상 장애:** JEUS가 힙 고갈로 **프로세스는 살아 있으나 요청에 응답하지 못하는** 상태. 현재는 운영자가 수동으로 `kill` 후 재기동하고 있다.

**자동 실행이 정당화되는 이유:** 이 조치는 **정상 서비스를 중단시키는 것이 아니라 이미 발생한 중단을 끝내는 것**이다. Phase 2의 다른 조치와 위험 성격이 근본적으로 다르며, 이것이 §7.3 결정의 근거다.

| ID | 요구사항 |
|---|---|
| **FR-2.9** | 자동 실행 조건은 **"이미 서비스 불능"이 메트릭으로 입증될 때로 한정**한다. 판정 기준은 §7.3 |
| **FR-2.10** | 조치 전 **포렌식 산출물을 먼저 수집**한다. 순서: `kill -3` ×3회(약 10초 간격) → `jmap -dump`(실패 시 `-F` 재시도) → `dmesg` / `hs_err_pid*` 수집 |
| **FR-2.11** | **포렌식은 복구를 막을 수 없다.** 모든 포렌식 단계에 타임아웃을 걸고, 실패하거나 시간을 초과하면 산출물 없이 종료·재기동으로 진행한다 |
| **FR-2.12** | 종료는 `kill -TERM` → 대기 → `kill -9` 순서를 따른다. **`jeusadmin`/stopServer 는 사용할 수 없다** — JVM이 응답해야 동작하는데 지금 상황이 바로 응답 불능이다 |
| **FR-2.13** | **재기동 폭주 차단** — 같은 서비스가 N분 이내 재발하면 재기동을 중단하고 사람에게 에스컬레이션한다. 힙을 빠르게 채우는 메모리 릭이면 무한 재기동 루프가 진짜 원인을 가린다 |
| **FR-2.14** | **이중화 인지** — 조치 전 반대편 노드의 건강 상태를 확인하고, 양쪽을 동시에 조치하지 않는다 |
| **FR-2.15** | **기동 중 억제** — JEUS 부팅은 수 분이 걸린다. 기동 완료 전까지 동일 대상에 대한 재탐지·재조치를 억제한다 |
| **FR-2.16** | **디스크 여유 공간 확인이 선행 조건**이다. 힙 덤프는 힙 크기만큼의 공간을 소비한다. 여유가 부족하면 힙 덤프를 건너뛰고 스레드 덤프만 남긴 뒤 진행한다 |
| **FR-2.17** | 스레드 덤프(`kill -3`)는 JVM의 stdout으로 출력된다. **기동 방식에 따라 `JeusServer.log` 일 수도 nohup 리다이렉트 파일일 수도 있으므로**, 대상별 출력 경로를 등록·수집 가능해야 한다 |

**포렌식 도구 선택 근거 (FR-2.10):**

`kill -3`(SIGQUIT)은 **스레드 덤프**를 만들며 "스레드가 무엇을 하고 있는지"만 알려준다. **"무엇이 힙을 채웠는지"는 알려주지 않는다.** 힙 내용은 `jmap -dump:format=b,file=...` 로만 얻을 수 있고, 응답 불능 JVM에는 attach가 붙지 않아 `jmap -F`(Serviceability Agent, 느리지만 멈춘 프로세스에도 동작)가 필요할 수 있다. 둘 다 JDK 1.7에서 지원된다. `jmap -dump` 는 stop-the-world이지만 **이미 응답을 못 하는 상태이므로 잃을 것이 없다.**

> **`-XX:+HeapDumpOnOutOfMemoryError` 가 이미 설정되어 있어도 이 절차가 필요하다.** 해당 옵션은 JVM이 실제로 `OutOfMemoryError` 를 **던질 때만** 작동한다. GC 데스 스파이럴은 힙이 99%에 붙어 Full GC만 반복할 뿐 예외 발생 조건에 걸리지 않을 수 있고, 이때 덤프가 없는 것은 정상 동작이다. 살아 있는 상태에서 능동적으로 떠야 하는 이유가 여기 있다.

**Phase 분류에 관하여:** `kill -3` / `jmap -dump` 는 서비스 상태를 바꾸지는 않지만 **JVM을 stop-the-world 시키고 대용량 파일을 쓴다.** 따라서 Phase 1의 읽기 전용 진단 카탈로그(FR-1.1)에 넣지 않고 **Phase 2 조치 시퀀스의 일부로만 분류**한다. 그렇지 않으면 "읽기 전용"이라던 Phase 1 도구가 운영 중인 JVM을 멈출 수 있게 되어 US-1.4·FR-1.1이 보장하려던 성질이 깨진다.

## 7. 결정 사항 및 열린 질문

### 7.1 Q1. 자율 실행용 자격증명 모델 — **결정: A안 (진단 전용 키쌍)**

검토했던 선택지:

| 선택지 | 내용 | 판정 |
|---|---|---|
| **A. 진단 전용 키쌍** | SSL 배포키와 분리된 별도 키쌍 + 전용 OS 계정. 설치 시 `authorized_keys` 등록 | **채택** |
| B. SSL 배포키 재사용 | 기존 `SSL_DEPLOY_KEY_PATH` 를 그대로 사용 | 기각 — 아래 ② ③ |
| C. 대화형 세션만 사용 | 사람이 로그인한 5분 세션에서만 진단 실행 | 기각 — 자율 예방(§1.2) 포기해야 함 |

**채택 근거:**

**① 등록 절차를 새로 만들지 않아도 된다.** `ssl_servers.py:112-142` 에 완성된 의식이 이미 있다. 최초 1회 비밀번호로 접속 → 공개키를 `authorized_keys` 에 append → `verify_key_auth()` 로 키 인증 확인 → 비밀번호 폐기(DB 저장 안 함). 그리고 agent-v 설치는 **이미 비밀번호 세션을 쓰고 있으므로**(`POST /agents/install` + `X-SSH-Session`, `_run_cli_install` 이 SFTP 업로드에 사용) 그 Job에 한 단계만 끼우면 된다.

**② 키를 나누면 침해 영향 범위가 실제로 좁아진다.** SSL 배포키는 웹서버 인증서 디렉터리 쓰기 + reload 실행 권한을 가지며 **DMZ 서버까지 포함**한다. 진단이 이 키를 재사용하면 진단 경로 침해가 곧 전 SSL 서버의 인증서 쓰기 권한 탈취가 된다.

**③ `authorized_keys` 는 키별 제약이 가능하다.** 진단 키에만 `restrict`(포트·에이전트 포워딩, PTY, X11 차단)를 걸 수 있다. SSL 배포키는 SFTP와 임의 reload 실행이 필요해 같은 제약을 걸 수 없으므로, 키를 공유하면 이 하드닝을 포기하게 된다. 그리고 Phase 2에서 강제 명령 디스패처(FR-1.14-b)로 2중 화이트리스트까지 갈 수 있는 여지는 **전용 키일 때만** 열려 있다.

> ③은 v1 시점에서는 보조 근거다. `command=` 는 명령 집합이 아니라 단일 명령을 강제하므로 v1 카탈로그와 양립하지 않아 채택하지 않았다(FR-1.14-a). **A안의 결정적 근거는 ②와 ④** 이며, ③이 약해져도 결론은 바뀌지 않는다.

**④ 비-root 원칙(NFR-6)과 맞는다.** 전용 계정이면 "이 계정이 무엇을 할 수 있나"를 sudoers 한 덩어리로 답할 수 있다. 인증서 배포까지 겸하는 계정은 그 질문에 답하기 어렵다.

> 참고: **만약 자율 예방을 포기하고 사람 시작 방식(챗봇 + ✨)만 유지한다면 C안으로 충분해지고 이 결정 전체가 불필요해진다.** A안이 옳은 이유는 목표가 자율 예방이기 때문이다. 목표가 바뀌면 이 결정을 재검토해야 한다.

구체적 요구사항은 §4.2 (FR-1.10 ~ FR-1.17) 참조.

### 7.2 Q2. v1 진단 카탈로그 범위 — **미결**

**권고: 무상태 조회 8~12개로 시작.** 후보 — 디스크 사용률, 메모리/스왑, 프로세스 존재 확인, 소켓 요약, **허용 경로 prefix(FR-1.3) 내 로그 tail**, 서비스 상태, 파일시스템 inode, 시스템 uptime/load.

함께 결정할 사항 — **시스템별 열람 허용 경로 prefix 집합의 초기값**. GC 로그·웹서버 에러로그처럼 agent가 수집하지 않는 경로를 포함시켜야 이 기능이 의미를 갖는다 (FR-1.3-a).

**제외 권고: `jstack` / `jmap` / `gcore`.** JVM을 일시 정지시켜 운영계에서 그 자체가 장애를 유발할 수 있다. 필요하다면 Phase 2(승인 필요) 항목으로 분류한다.

### 7.3 Q3. 조치 실행 방식 (Phase 2) — **결정: C안 (조건부 자동 + 기본 승인)**

| 선택지 | 판정 |
|---|---|
| A. 전부 승인 후 실행 | rev.2 권고안. rev.3에서 **부분 채택** — 기본값으로 유지 |
| B. 실행 후 통보 | 기각 — LLM 오판이 곧바로 운영 사고가 된다 |
| **C. 등급별 혼합** | **채택** — rev.2에서 "저위험 판정 기준이 논쟁거리"라며 보류했으나, 아래 기준으로 해소됨 |

**자동 실행 허용 기준:**

> **동일한 메트릭으로 "해당 서비스가 이미 정상 동작하지 않음"이 입증되는 조치만 자동 실행을 허용한다.**

이 기준이 rev.2의 난점을 푼다. "저위험"은 사람의 주관적 판정이지만, **"이미 서비스 불능"은 `http_request_total{status_code, was_service}` 로 기계가 검증할 수 있는 조건**이다. 그리고 이 조건이 성립하면 조치의 성격 자체가 바뀐다 — **정상 상태를 훼손하는 것이 아니라 이미 발생한 장애를 종료시키는 것**이 되므로, 승인 대기 시간이 곧 장애 지속 시간이 된다.

**적용 규칙:**

| ID | 요구사항 |
|---|---|
| **FR-2.18** | **기본값은 승인 후 실행**이다. 자동 실행은 카탈로그 항목별로 명시적으로 부여하는 예외이며, 부여 조건은 위 기준을 만족함을 근거와 함께 기록해야 한다 |
| **FR-2.19** | 자동 실행 항목도 **감사·타임라인 기록·사후 통보는 동일하게 수행**한다. 승인이 생략될 뿐 추적이 생략되지 않는다 |
| **FR-2.20** | 자동 실행은 **항목 단위로 즉시 비활성화**할 수 있어야 하며, 비활성화 시 해당 항목은 승인 게이트로 강등된다(기능이 사라지는 것이 아니라) |
| **FR-2.21** | 승인이 필요한 항목의 승인 UI는 **프론트엔드 승인 화면**을 사용한다. Teams Adaptive Card 버튼은 카드 URL을 아는 사람이면 누구나 누를 수 있어 인증 경계가 약하므로 상태 변경 트리거로 쓰지 않는다 |

**초기 자동 실행 항목:** §5.3 JEUS 행 복구 **1건뿐**이다. 다른 항목의 추가는 운영 데이터가 쌓인 뒤 개별 심사한다.

## 9. 순차 로드맵

각 단계는 앞 단계의 결과에 의존한다. **병렬로 진행하지 않는다** — 특히 Step 0의 결과가 Step 1의 필요 여부 자체를 바꾼다.

### Step 0. 실패 원인 판별 — **비용 0, 최우선**

다음 장애 발생 시 아래 순서로 확인한다. 별도 개발이 필요 없다.

1. `hs_err_pid<pid>.log` 존재 → JVM 크래시
2. `dmesg` / `/var/log/messages` 의 `Out of memory: Killed process ... (java)` → **커널 OOM Killer**
3. `JeusServer.log` 의 `java.lang.OutOfMemoryError` → JVM 힙 부족 확정
4. 셋 다 없음 → 외부 `kill` 또는 정상 종료 (exit status 확인)

**분기:** 2번(커널 OOM Killer)이면 **Step 1 전체가 불필요하다.** JVM 힙은 멀쩡한데 호스트 물리 메모리가 고갈된 것이므로 이미 수집 중인 `memory_used_bytes` 로 충분하고, 과제가 호스트 메모리 관리로 바뀐다. 3번이면 Step 1로 진행한다.

> 상세 근거는 `docs/jvm-metrics-collection-decision.md` §2.

### Step 1. JVM 힙·GC 메트릭 수집 — **탐지 신호 확보**

Step 0에서 JVM 힙 문제가 확정된 경우에만 진행. 별도 문서로 분리했다: **`docs/jvm-metrics-collection-decision.md`**

권고안은 GC 로그 tailing이며, 확정에는 **synapse-agent의 실행 OS 계정** 확인이 필요하다(해당 문서 §6).

이 단계가 없으면 "사전 인지"가 성립하지 않는다. 현재 신호로는 **탐지는 되지만 예측은 안 된다.**

### Step 2. 탐지 규칙 정립

Step 1의 메트릭 + 기존 신호(`http_request_total` 5xx·요청량, `process_cpu_percent`, `process_zombie_by_parent`)를 조합해 두 가지를 정의한다.

- **예측 규칙** — "곧 힙이 터진다" (선행 경보용, 조치 없음)
- **자동 실행 판정 규칙** — "이미 서비스 불능이다" (§7.3 자동 실행 허용 조건). **오탐이 곧 정상 노드 종료이므로 보수적으로 잡는다**

### Step 3. Phase 1 — 읽기 전용 진단

Q2(진단 카탈로그 + 시스템별 열람 허용 경로 prefix) 확정 후 착수. 승인 게이트가 없어 단독 출시 가능하다.

### Step 4. Phase 2 — JEUS 행 복구 자동화

§5.3 카탈로그 항목 구현. Step 2의 판정 규칙이 검증된 뒤에 착수한다.
