# 슬라이드 3 — Why ① 현재 운영 환경의 4가지 한계

## 타이틀
"수많은 시스템 · 수많은 알림 · 흩어진 노하우"

## 본문
1. **모니터링 사일로** — 메트릭(Prometheus²) / 로그가 따로 존재. 한 장애를 추적하려면 여러 곳을 옮겨다녀야 함
2. **알림 피로(Alert Fatigue)** — ERROR 로그가 모두 알림으로 발송되어 진짜 위급 상황이 묻힘. 운영팀이 알림을 무시하기 시작
3. **노하우 휘발** — 베테랑 담당자가 해결한 장애가 사람의 머릿속에만 남음. 인사이동·퇴사 시 조직 자산 손실
4. **사후 대응** — 장애가 터진 뒤에야 인지. "왜 일어났는가" 추론은 수작업, 재발 방지는 회의록에만

## 레이아웃
```
┌────────────────────────────────────────────────┐
│   [현재]                                       │
│                                                │
│   📊 Grafana    📝 로그파일    🔔 Teams        │
│        │             │              │          │
│        └────?────────┴──────?───────┘          │
│              "어디서 봐야 하지?"                │
│                                                │
│   🔥 알림 100건/일 ── 진짜 위험은 5건           │
│   🧠 노하우 → 베테랑 담당자 머릿속              │
│   ⏰ 장애 인지 → Teams 보고 후 수작업 분석     │
│                                                │
└────────────────────────────────────────────────┘
```

## 발표자 노트
"운영팀이 매일 마주하는 현실입니다. 모니터링 도구가 분산되어 있어 한 장애를 분석하려면 Grafana, 로그서버, Teams를 번갈아 보아야 합니다. 알림은 너무 많아 무뎌지고, 베테랑 담당자가 어렵게 해결한 장애 노하우는 다음 사람에게 전달되지 않습니다."

> ² **Prometheus** — 시계열 메트릭(CPU·메모리·트래픽 등) 수집·저장 오픈소스. 백화점 IT 인프라 표준으로 이미 운영 중.

# 슬라이드 4 — Why ② 임원 관점에서 본 숨은 비용

## 타이틀
"보이지 않는 운영 비용이 누적된다"

## 본문
- **장애 영향 시간 증가** — 인지 지연 + 분석 지연 = 매출·고객 신뢰 손실
- **반복 장애** — 같은 원인의 장애가 분기마다 재발 (조치는 했으나 조직에 남지 않음)
- **인적 비용** — 운영팀이 "알림 분류"와 "로그 검색"에 시간을 소진. 본질 업무인 안정화·개선 작업이 후순위로 밀림
- **의사결정 지연** — 임원진이 "지금 우리 시스템 안전한가?"에 즉답할 수 없음. 매일 아침 운영팀 보고를 기다려야 함
- **지식 의존성** — 특정 인력이 부재하면 장애 대응 속도가 급격히 저하

## 레이아웃
```
┌──────────────────────────────────────────────┐
│ "지금 우리 시스템, 안전한가요?"              │
│                                              │
│  ┌─────────────┐  ┌─────────────┐          │
│  │ 매출 영향   │  │ 고객 신뢰    │          │
│  │  ↓ 장애시간 │  │  ↓ 반복장애  │          │
│  └─────────────┘  └─────────────┘          │
│  ┌─────────────┐  ┌─────────────┐          │
│  │ 인적 비용   │  │ 지식 의존    │          │
│  │  ↓ 알림분류 │  │  ↓ 1人 의존  │          │
│  └─────────────┘  └─────────────┘          │
│                                              │
│  결국 → 의사결정 정보가 항상 한 발 늦음      │
└──────────────────────────────────────────────┘
```

## 발표자 노트
"이런 운영 환경은 단순한 기술 부채가 아닙니다. 매출에 직결된 시스템 다운타임, 같은 장애가 반복되며 누적되는 신뢰 손실, 그리고 무엇보다 임원진이 '지금 우리 시스템이 안전한가'라는 질문에 즉시 답할 수 없다는 점이 가장 큰 비용입니다."

# 슬라이드 5 — Why ③ 왜 지금이 적기인가

## 타이틀
"AI 모델 + 폐쇄망 인프라 = 지금 도입 가능"

## 본문
- **LLM³의 운영 분석 능력 성숙** — 로그 텍스트와 메트릭 패턴을 사람이 읽는 수준으로 자동 해석 가능
- **벡터 검색 인프라 안정화** — Qdrant⁴ 같은 오픈소스 벡터 DB가 폐쇄망에서 안정 동작 확인
- **사내 LLM 채널(DevX) 확보** — 외부 API 의존 없이 내부망에서 LLM 활용 가능
- **컨테이너 표준화** — 폐쇄망 RedHat 8.9 환경에서 Docker 단일 이미지 번들로 배포 가능

## 레이아웃
```
┌──────────────────────────────────────────────┐
│ "기술적 전제가 모두 갖춰진 시점"             │
│                                              │
│ ┌─────────────────────────────────────────┐ │
│ │ ① LLM   →  로그/메트릭 자연어 분석      │ │
│ │ ② Qdrant →  유사 장애 벡터 검색         │ │
│ │ ③ DevX   →  사내 폐쇄망 AI 채널         │ │
│ │ ④ Docker →  폐쇄망 무중단 배포          │ │
│ └─────────────────────────────────────────┘ │
│                                              │
│       네 조각이 동시에 도착했다              │
└──────────────────────────────────────────────┘
```

## 발표자 노트
"세 가지 기술 흐름이 동시에 무르익었습니다. LLM은 로그를 사람처럼 읽을 수 있게 됐고, 벡터 검색은 폐쇄망에서도 안정 동작하며, 사내 DevX 채널 덕분에 외부 API 의존 없이 AI를 활용할 수 있습니다. 이 시점에 통합 플랫폼을 구축하는 것이 가장 효율적입니다."

> ³ **LLM (Large Language Model)** — 대규모 언어 모델. 자연어 문장을 사람처럼 이해하고 생성하는 AI. 본 시스템은 외부 API 대신 사내 DevX 채널을 통해 호출.
> ⁴ **Qdrant** — 오픈소스 벡터 데이터베이스. "의미가 비슷한" 텍스트를 빠르게 찾는 용도. 본 시스템에서 과거 장애 이력·해결책을 의미 기반으로 검색하는 데 사용.

# 슬라이드 6 — What ① Synapse-V 한 장 요약

## 타이틀
"메트릭 · 로그를 AI가 한 화면에서 분석한다"

## 본문
**Synapse-V는 세 가지 일을 동시에 한다**
1. **수집·통합** — 모든 백화점 운영 시스템의 메트릭/로그를 한곳에 모음
2. **자동 분석 & 제안** — LLM이 5분 주기로 이상 징후를 분석하고 담당자에게 Teams로 원인·조치를 자연어로 제안
3. **지식 자산화** — 담당자가 등록한 해결책을 벡터 DB(Qdrant)에 저장 → 다음 유사 장애 발생 시 자동 매칭

> 단순한 모니터링 도구가 아니라, **운영팀의 AI 동료**.

## 레이아웃
```

│                                              │

│   │메트릭  │      │  LLM   │    │ Qdrant │  │
│   │  로그  │ ─→   │ 분석   │ ─→ │  RAG   │  │
│   │        │      │ +제안  │    │  검색  │  │
│   └────────┘      └────────┘    └────────┘  │
│        ↓               ↓             ↓       │
│   대시보드        Teams 알림      챗봇       │
│                                              │
│   "운영팀의 AI 동료"                          │
└──────────────────────────────────────────────┘
```

## 발표자 노트
"Synapse-V를 한 줄로 정의하면 '운영팀의 AI 동료'입니다. 단순히 알림만 보내는 도구가 아니라, 데이터를 통합하고, AI가 분석·제안하며, 담당자의 노하우를 다음 사람에게 자동으로 전달합니다."

# 슬라이드 7 — What ② 핵심 기능 5가지

## 타이틀
"5가지 핵심 기능 매트릭스"

## 본문
| # | 기능 | 사용자 가치 |
|---|------|-------------|
| 1 | **통합 대시보드** | 전사 시스템 상태를 한 화면에서 즉시 판단 |
| 2 | **AI 자동 분석 + Teams 알림** | LLM이 장애 원인을 사람이 읽는 문장으로 자동 작성, 조치 제안 |
| 3 | **인시던트 라이프사이클** | 장애를 "사건" 단위로 추적, MTTA/MTTR⁵ 측정 |
| 4 | **운영지식 RAG 챗봇** | 자연어 질문으로 과거 장애·해결책 즉시 검색 (담당자용 + 현장직원 게스트용) |
| 5 | **계층 집계 + 장애 예방 알림** | **1시간 / 1일 / 7일 / 30일** 단위 자동 집계 → 추이 분석 → 사전 경고 |

## 레이아웃
```
┌──────────────────────────────────────────────────┐
│ Synapse-V 5대 핵심 기능                          │
├──────────────────────────────────────────────────┤
│  [1] 통합 대시보드    │ 전사 상태 한눈에         │
│  [2] AI 자동 분석     │ LLM이 원인·조치 제안     │
│  [3] 인시던트 추적    │ MTTA/MTTR 측정           │
│  [4] 운영지식 챗봇    │ 자연어로 노하우 검색     │
│  [5] 계층 집계+예방   │ 1h/1d/7d/30d 추이 분석   │
├──────────────────────────────────────────────────┤
│ + 운영 자동화: SSH 기반 수집기 Agent 일괄 배포    │
│ + 보안: OIDC⁶ IdP로 타시스템 SSO 제공            │
└──────────────────────────────────────────────────┘
```

## 발표자 노트
"5대 기능을 매트릭스로 정리했습니다. 5번 기능은 1시간/1일/7일/30일 네 가지 시간 창 모두에서 자동 집계와 추이 분석이 돌아가, 단기 변화부터 장기 패턴까지 사전 감지가 가능합니다. 다음 3개 슬라이드에서 가장 핵심 화면 3개 — 대시보드, 인시던트, 챗봇을 와이어프레임과 함께 보여드리겠습니다."

> ⁵ **MTTA / MTTR** — Mean Time To Acknowledge(감지→확인 평균 시간) / Mean Time To Resolve(감지→해결 평균 시간). 운영 품질의 표준 KPI.
> ⁶ **OIDC (OpenID Connect)** — 사용자 신원 확인을 표준화한 SSO(Single Sign-On) 프로토콜. 한 번 로그인하면 여러 시스템을 추가 로그인 없이 사용. Synapse-V가 다른 사내 시스템의 인증 허브 역할 수행.

# 슬라이드 9 — What ④ 화면 2: 인시던트 라이프사이클

"장애를 '사건' 단위로 추적 — MTTA/MTTR 측정"

## 본문

- **MTTA·MTTR 자동 계산** — 운영 KPI 자동 측정

# 슬라이드 10 — What ⑤ 화면 3: 운영지식 RAG 챗봇

## 타이틀
"자연어로 묻고, AI가 과거 노하우로 답한다"

## 본문
- **인증 사용자(운영팀)용 챗봇** — 다중 시스템 스코프 선택, 세션 저장·검색·이름변경, 메시지 스트리밍, 첨부파일
- **게스트(현장 직원)용 챗봇** — 사번만으로 입장, 24시간 이내 이전 대화 이어가기, 담당자 에스컬레이션 버튼
- **백엔드 RAG**: Qdrant Hybrid Search⁷ + ReAct 도구 체인⁸ — 정책 / 메트릭 / 해결책 통합 검색
- **AI Agent의 도구 토글**: 외부 시스템 연동 도구를 관리자 페이지에서 활성·비활성 제어
- **운영지식 자산화**: 담당자가 해결책을 한 번 등록 → 다음 유사 장애 발생 시 자동 검색·제안

## 레이아웃
```
┌──────────────────────────────────────────────────┐
│ [≡ 세션]  지식검색대상: [시스템1 시스템2...]    │
├────────────┬─────────────────────────────────────┤
│ 최근 대화  │ 사용자: "어제 발생한 OOM 원인?"    │
│ ─ 대화 A   │                                     │
│ ─ 대화 B   │ 🤖 (AI Agent 추론)                 │
│ ─ 대화 C   │ 🛠 (도구) admin_search_alerts      │
│ [검색]     │ 🛠 (도구) qdrant_search_incident   │
│            │                                     │
│            │ 💬 "유사 사건이 3건 있었습니다.    │
│            │    공통 원인은 JVM 힙 설정 누락,   │
│            │    제안 조치는 -Xmx 4g 적용입니다." │
│            │                                     │
│            │ [메시지 입력...]    [📎 첨부]      │
└────────────┴─────────────────────────────────────┘
```

## 발표자 노트
"이 챗봇이 Synapse-V의 가장 차별화된 기능입니다. 화면의 'AI Agent'는 챗봇 내부에서 자동으로 도구를 골라 호출하는 LLM 에이전트로, 서버에 설치되는 '수집기 Agent'와는 다릅니다. 담당자가 한 번 해결책을 등록하면, 다음 사람이 같은 증상을 겪을 때 챗봇이 자동으로 과거 사례를 찾아 답변·제안합니다."

> ⁷ **Hybrid Search** — 의미 기반 검색(Dense)과 키워드 매칭(Sparse BM25)을 결합한 검색 방식. 'NullPointerException' 같은 정확 키워드와 '메모리 부족 같은 증상' 같은 의미 검색을 동시에 만족.
> ⁸ **ReAct (Reasoning + Acting)** — AI가 "생각 → 도구 호출 → 결과 관찰 → 다시 생각"의 순환으로 복잡한 질문에 답하는 방식.

# 슬라이드 12 — How ② 데이터 흐름 1: 메트릭/로그 → AI → 알림

## 타이틀
"5분 주기 자동 분석 + 제안 파이프라인"

## 본문
1. **수집** — synapse-수집기 Agent가 대상 서버의 CPU/메모리/디스크/네트워크/로그 → Prometheus
2. **이상 감지** — log-analyzer가 5분마다 `log_error_total` 메트릭을 조회 → PII 자동 마스킹
3. **벡터 검색** — Qdrant Hybrid 검색으로 유사 과거 장애 매칭 (duplicate / recurring / related / new 자동 분류)
4. **LLM 분석·제안** — 사내 DevX LLM에 프롬프트 전송 → 원인 + 조치 자연어 생성·제안
5. **알림 + 저장** — Teams Adaptive Card로 담당자 @멘션 발송 + DB·Qdrant에 영속

## 레이아웃
```
┌────────────────────────────────────────────────┐
│  [수집 → 분석·제안 → 알림] 5분 주기            │
│                                                │
│  ① synapse-수집기 Agent  ──▶  Prometheus       │
│                                                │
│  ② log-analyzer 스케줄러 (5분)                 │
│       │                                        │
│       ├─ PII 마스킹 (카드/주민/전화/이메일)    │
│       │                                        │
│  ③   ├─ Qdrant Hybrid 유사도 검색             │
│       │   (duplicate/recurring/related/new)    │
│       │                                        │
│  ④   ├─ DevX LLM 호출                         │
│       │   "원인 + 조치 자연어 제안"            │
│       │                                        │
│  ⑤   └─ Teams 발송 + DB 저장                  │
│            (@담당자 멘션)                      │
└────────────────────────────────────────────────┘
```

## 발표자 노트
"5분마다 자동으로 동작하는 핵심 파이프라인입니다. 주목할 점 두 가지: 첫째, LLM에 보내기 전 카드번호·주민번호 등 PII를 자동 마스킹합니다. 둘째, 동일·반복 장애는 자동 분류되어 같은 알림이 5분 내 중복 발송되지 않습니다(쿨다운). 운영팀의 알림 피로를 구조적으로 줄였습니다."

# 슬라이드 13 — How ③ 데이터 흐름 2: 벡터 RAG (지식 자산화)

## 타이틀
"담당자가 등록한 해결책이 다음 장애에 자동 활용된다"

## 본문
- **저장**: 장애 발생 → 담당자가 Teams 카드 "해결책 등록" 클릭 → React 페이지로 이동 → 원인·조치 입력 → Qdrant 벡터로 영속
- **검색**: 다음 유사 장애 발생 → log-analyzer가 자동 Hybrid 검색 → LLM 프롬프트에 과거 해결책 주입 → 더 정확한 제안 생성
- **챗봇 활용**: 운영지식 챗봇에서도 같은 Qdrant 컬렉션 활용 → "이 증상 본 적 있어?" 자연어 검색
- **하이브리드 검색의 강점**: 에러 클래스명(NullPointerException, ORA-00060) 정확 매칭(BM25⁹) + 의미 검색(Dense¹⁰) 동시 확보

## 레이아웃
```
┌────────────────────────────────────────────────┐
│       지식 자산화 RAG 사이클                   │
│                                                │
│   장애 발생                                    │
│      ↓                                         │
│   Teams 알림 → 담당자가 [해결책 등록] 클릭     │
│      ↓                                         │
│   React 페이지에서 원인·조치 입력              │
│      ↓                                         │
│   ┌──────────────────────────────────────┐   │
│   │  Qdrant Hybrid Collection            │   │
│   │  Dense (의미)  +  Sparse BM25 (키워드)│   │
│   └──────────────────────────────────────┘   │
│      ↓                          ↓              │
│   다음 장애 자동 매칭     챗봇이 자연어 검색   │
│   (LLM 프롬프트 주입)     ("OOM 본 적 있어?") │
│                                                │
│   ➜ 노하우는 한 번 등록, 영구 활용             │
└────────────────────────────────────────────────┘
```

## 발표자 노트
"이 사이클이 Synapse-V의 핵심 차별점입니다. 담당자가 등록한 해결책이 두 가지 경로로 재사용됩니다: 첫째, 다음 유사 장애 발생 시 자동으로 LLM 프롬프트에 주입되어 더 정확한 자동 분석·제안을, 둘째, 챗봇이 자연어 질문에 과거 사례 기반으로 답변합니다."

> ⁹ **BM25 (Best Matching 25)** — 키워드 출현 빈도·희귀도를 가중치로 매기는 전통 검색 알고리즘. 정확한 단어가 들어간 문서를 빠르게 찾는 데 강함.
> ¹⁰ **Dense Embedding** — 문장을 1024차원 숫자 벡터로 변환해 "의미가 비슷한 정도"를 거리로 계산. 단어가 달라도 비슷한 의미면 높은 유사도가 나옴.

# 슬라이드 14 — How ④ AI 파이프라인의 유연성

## 타이틀
"LLM 프로바이더 교체 가능 + 업무영역별 전문 AI Agent"

## 본문
- **Strategy 패턴¹¹ LLM 라우팅** — 환경변수 `LLM_TYPE` 한 줄 변경으로 DevX / Claude / OpenAI 전환 가능
- **업무 영역별 AI Agent (9종)** — 로그 분석 / 메트릭 분석 / 트렌드 예측 / 일별 리포트 / 챗봇 등 영역별로 전용 LLM 에이전트 분리 → 영역마다 다른 모델·프롬프트 적용 가능
- **담당자별 LLM 키 (선택)** — 비용 분리·감사 추적 목적
- **분석 실패 가시화** — LLM 호출 실패도 DB에 기록 → 운영자가 어느 시스템 분석이 실패하는지 즉시 파악
- **인적 검증 사이클** — AI는 "제안"만 하고, 담당자가 채택·수정 → 잘못된 제안은 다음 분석에서 자동 보정

# 슬라이드 15 — How ⑤ 운영·관리 자동화

## 타이틀

- **synapse-cli 일괄 배포** — 운영자 터미널 챗봇용 CLI 바이너리를 여러 서버에 한 번에 배포·업데이트
- **타시스템 SSO 제공 (OIDC IdP)** — 다른 사내 시스템이 Synapse 계정으로 로그인 가능 → 통합 인증 허브 역할

# 슬라이드 16 — How ⑥ 안정성과 확장성 설계 원칙

## 타이틀
"의사결정을 기록하고, 실패를 가시화한다"

## 본문
- **ADR(아키텍처 결정 기록)¹² 17건** — 모든 핵심 설계 결정을 배경·결정·트레이드오프 형식으로 기록 → 인수인계 시 의도 보존
- **3중 동기화 스키마 관리** — ORM + init.sql + migration SQL 동시 변경 → 신규 설치와 기존 운영 DB 모두 일관 유지
- **타임존 정책 표준화** — 저장=UTC / 스케줄=KST / 표출=KST 명문화 → 9시간 오차 버그 차단
- **에러 가시화** — LLM 호출 실패, 벡터 저장 실패 등 모든 실패 경로가 DB·UI에서 추적 가능
- **모듈화** — 새 LLM 프로바이더, 새 수집기 Agent, 새 챗봇 도구를 코드 수정 없이 등록 가능 (Strategy + Registry 패턴)

## 레이아웃
```
┌──────────────────────────────────────────────┐
│  설계 원칙: "기록 · 가시화 · 모듈화"         │
│                                              │
│  📚 ADR 17건                                 │
│     모든 결정을 배경·결정·트레이드오프 기록   │
│                                              │
│  🔄 3중 동기화 스키마                        │
│     ORM + init.sql + migration SQL          │
│                                              │
│  🌏 타임존 정책 표준화                        │
│     저장=UTC / 스케줄=KST / 표출=KST         │
│                                              │
│  🔍 에러 가시화                              │
│     LLM 실패도 DB+UI에서 추적                 │
│                                              │
│  🔌 모듈화 (Strategy + Registry)             │
│     새 LLM/수집기 Agent/도구 코드없이 추가    │
└──────────────────────────────────────────────┘
```

## 발표자 노트
"이런 설계 원칙이 중요한 이유는 시스템의 수명이 깁니다. 17건의 아키텍처 결정 기록으로 '왜 이렇게 만들었는가'를 보존했고, 모든 실패 경로를 가시화해 운영 중 문제를 즉시 파악할 수 있도록 했습니다. 모듈화 덕분에 새 기능 추가 시 기존 코드를 건드리지 않고 확장할 수 있습니다."

> ¹² **ADR (Architecture Decision Record)** — 아키텍처 결정의 배경·선택·트레이드오프를 짧은 문서로 남기는 표준 관행. 시간이 지나도 "왜 이렇게 했는지"를 잃지 않게 함.

# 슬라이드 17 — 기대효과 ① 운영 효율 개선

## 타이틀
"알림 노이즈는 줄이고, 대응 속도는 높인다"

- **장애 인지 속도 개선** — 메트릭 + 로그가 한 화면에 통합되어 "왜 일어났나" 추론 시간 단축
- **현장 업무 부담 완화** — 게스트 챗봇으로 매장 직원이 운영팀 호출 전에 1차 자가 해결 가능
- **자동 인시던트 묶음** — 같은 시스템의 연쇄 알림이 한 사건으로 관리 → 우선순위 판단 명확
- **Teams @멘션 정확 라우팅** — 시스템별 담당자 자동 호출 → "누가 봐야 하나" 의사소통 비용 제거

## 레이아웃
```

│  운영 효율 개선                              │
│                                              │
│   [Before]                  [After]          │
│  ─────────────             ─────────────     │
│   알림 폭주               알림 분류·쿨다운   │
│   원인 추론 수작업    →   AI 자동 분석·제안  │
│   누가 볼지 갑론을박      Teams @담당자 멘션 │
│   현장→운영팀 즉시 호출   1차 챗봇 자가해결  │

│                                              │
│  ➜ 운영팀이 본질 업무에 집중                  │
└──────────────────────────────────────────────┘
```

- **지식 검증 사이클** — 관리자가 부정확한 해결책을 감수·승인 → 챗봇 답변 신뢰도 점진적 개선
- **운영 정책·매뉴얼 통합 관리** — 가이드 / 자주묻는질문 / 운영자 노트가 한 곳에서 RAG 활용

# 부록 A — 용어집 (각주 통합본)

발표 중 자주 등장하지만 임원진에게 익숙하지 않을 수 있는 기술 용어를 한 곳에 모았습니다. 슬라이드 노트에 1~2줄로만 노출하고, 상세 설명이 필요한 임원께는 본 부록을 별도 인쇄 제공.

| 용어 | 한 줄 설명 |
|---|---|
| **RAG** (Retrieval-Augmented Generation) | AI가 답변 전 관련 자료를 먼저 검색해, 그 내용을 근거로 답하는 방식. 환각을 줄이고 사내 지식 기반 답변이 가능. |
| **Prometheus** | 시계열 메트릭(CPU·메모리 등) 수집·저장 오픈소스 표준. 사내에서 이미 사용 중. |
| **LLM** (Large Language Model) | 대규모 언어 모델. 자연어를 사람처럼 이해·생성하는 AI. 본 시스템은 사내 DevX 채널을 통해 호출. |
| **Qdrant** | 오픈소스 벡터 데이터베이스. "의미가 비슷한" 텍스트를 빠르게 찾는 용도. 폐쇄망에서 안정 동작. |
| **Hybrid Search** | 의미 기반 검색(Dense) + 키워드 매칭(Sparse BM25)의 결합. 정확한 단어와 비슷한 의미를 동시에 찾음. |
| **Dense Embedding** | 문장을 1024차원 숫자 벡터로 바꿔 의미적 거리를 계산. 단어가 달라도 비슷한 의미면 유사도가 높음. |
| **BM25** | 키워드 출현 빈도·희귀도 기반 전통 검색 알고리즘. 정확한 단어 매칭에 강함. |
| **MTTA / MTTR** | Mean Time To Acknowledge(감지→확인) / Mean Time To Resolve(감지→해결) 평균 시간. 표준 운영 KPI. |
| **OIDC** (OpenID Connect) | 사용자 신원 확인 표준 SSO 프로토콜. 한 번 로그인으로 여러 시스템 사용. Synapse-V가 사내 인증 허브 역할. |
| **ReAct** | AI Agent가 "생각 → 도구 호출 → 결과 관찰 → 다시 생각"의 순환으로 복잡한 질문에 답하는 방식. |
| **Strategy 패턴** | 같은 인터페이스의 여러 구현체를 환경설정으로 교체할 수 있게 하는 소프트웨어 설계 기법. |
| **ADR** (Architecture Decision Record) | 아키텍처 결정의 배경·선택·트레이드오프를 짧게 남기는 문서 관행. |
| **수집기 Agent** | 대상 서버에 설치되어 메트릭/로그를 수집하는 프로그램 (Synapse-V는 Rust 단일 바이너리). |
| **AI Agent** | 챗봇 내부에서 도구를 자동으로 골라 호출하는 LLM 에이전트. 수집기 Agent와 다름. |
| **PII** (Personally Identifiable Information) | 개인 식별 정보(카드/주민/전화/이메일). 본 시스템은 LLM 호출 전 자동 마스킹. |

# 부록 B — 자주 받을 만한 질문 미리 답변

1. **"외부 LLM에 사내 데이터가 나가나요?"** → 사내 DevX 채널 사용, 외부망 차단. PII는 LLM 호출 전 자동 마스킹.
2. **"기존 Grafana는 폐기되나요?"** → 아닙니다. Grafana 대시보드는 Synapse-V 화면 안에 임베드되어 그대로 활용.
3. **"새 서버 추가는 누가 하나요?"** → 운영팀이 SSH 세션 한 번 등록 후 브라우저 [설치] 버튼으로 5분 내 완료(수집기 Agent 자동 배포).
4. **"AI 분석이 틀리면요?"** → AI는 "제안"만 하고 결정은 담당자가 합니다. 분석 실패도 DB에 기록되고 UI에 빨간 배지로 표시. 담당자가 수정한 해결책이 다음 분석에 반영.
5. **"도입 후 운영팀 인력이 줄어드나요?"** → 인력 감축이 아니라, 같은 인력이 알림 분류 대신 안정화·개선 업무에 시간을 쓸 수 있게 함.
6. **"수집기 Agent와 AI Agent는 같은 건가요?"** → 다릅니다. 수집기 Agent는 서버에 설치되어 데이터를 수집하는 프로그램, AI Agent는 챗봇 내부에서 도구를 호출하며 답변을 만드는 LLM 에이전트입니다.
7. **"트렌드 분석은 얼마나 자주 보나요?"** → 1시간 / 1일 / 7일 / 30일 4가지 시간 창에서 자동으로 집계되며, 4시간마다 LLM이 추이를 분석해 사전 알림을 보냅니다.
